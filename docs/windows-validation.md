实际遇到的问题：默认 Debug 构建额外要求 GodotSharpEditor，而现有 packages.lock.json 对应 Release，出现 NU1004。两平台构建入口改为默认 Release，与 pack 和锁文件一致；没有删锁或放宽依赖版本。

后续清洁打包曾在已经保存 PCK 后因 EditorSettings 原生错误退出 -1，不能因文件存在就算成功。将首次资源导入独立为 `--headless --editor --import`，完成后再 `--export-pack`；两个步骤都严格检查退出状态。修改后连续三次清洁打包退出 0，资源检查通过；内部竞态原因尚未独立证明。

`./tools/build.ps1 build` 与 `./tools/build.ps1 pack` 已通过。资源包在独立无 C# Godot 工程挂载，中文/英文 JSON 与导入的 PNG 实际读取通过。产物位于 `dist/Shenshen/` 和 `dist/BaseLib/`；这些结果证明编译与资源有效，不等同游戏机制验收。

## 代码实现

- 独立 `ShenshenCardPool`；少女小火球、光之护盾各 5 张，猫爪击、咪闪各 5 张，永久 Deck 共 20 张实际卡。变形牌为额外生成的单张战斗功能牌，不替代任一形态牌组。
- 开场少女、70 HP、3 能量、正常抽牌 5 张；变形 1 费，保留，结算回手。当前形态专属手牌正常弃置，目标形态补抽同数量；资源、增益与负面不重建。
- 两形态抽弃循环使用原版五个受追踪牌堆内的子序列，普通抽牌、洗牌和自动出牌仅选择活跃形态/共享牌。所有移动保留同一卡牌实例及升级、费用等状态；没有随机猫牌替换。
- 形态、闪避是否使用、炸毛本场首次是否已触发均储存在原生 Power.Amount，而不是进程内弱引用表；卡牌留在原版追踪堆中。本机 NetFullCombatState 包含这些 Amount，主要用于联机校验与分歧诊断，不是自动恢复快照。实现依赖原生确定性动作和状态校验，尚未完成真实双端或重连验收。
- 猫闪避移除多段攻击首段的目标，跳过伤害接收流水线，使该段既不消耗格挡也不触发荆棘/镜反伤。变形不重置，主人下回合抽牌前刷新。
- 炸毛仅敌方攻击实际扣血触发：生效后整场首次 +3 荆棘，后续每次 +1；敌方成功施加每种负面另 +1，独立于首次标记。自伤、中毒扣血、塞状态牌不走这些触发；免疫后实际变化为零不触发。
- 不喜欢你！按本机 FightMe 数值；光之镜 2 能量、15/20 格挡，复用实际格挡伤害反射；多人祝福 1 费普通，仅其他队友，目标下回合抽牌前用原生同步选牌移动其原卡。

未确认细节按 [角色设计的原型选择](character-design.md#windows-原型选择2026-11-05未作为用户确认规则) 实现。占位美术、燃烧之血和原版遗物/药水池未作为正式设计。

## 自动回归与游戏界面实测

真实程序集回归运行于独立 MegaDot headless 工程，挂载本机游戏/BaseLib/本模组资源，初始化真实模型、玩家、牌堆、敌人与 Harmony 补丁。它测试实际机制方法，不是用一个模拟牌组重写实现。

最终 `./tools/test.ps1` 退出 0，**45 项通过**，主工程与测试工程构建均为 0 警告、0 错误。覆盖两套实际持有牌、9 次换牌后的实例集合与数量、升级/费用状态、共享牌与空牌堆、手牌上限、标准三张奖励与商店五槽、变形牌实际打出回手、四张基础牌、不喜欢你！基础/升级、镜的格挡与反射、猫闪避跨 await 及不触发反伤、炸毛跨回合首次/负面独立/免疫/自伤边界、祝福拒绝自身与队友叠层、双玩家诊断数据包往返。

保存验证走真实 `RunManager.ToSave` → `SaveManager.ToJson/FromJson<SerializableRun>` → `Player.FromSerializable`：永久少女 10 张、猫 10 张以及其中一张升级均保持。测试没有假装恢复完整地图/房间。原版本机在地图点/房间边界保存永久牌组；该保存格式不含当时手/抽/弃牌堆与形态 Power，**本轮不实现战斗中快照恢复**。退出重进完整 run 以及真实双端重连仍待界面验收。

独立测试进程引用实际 v0.111.0 DLL，但 BaseLib 在编辑器可执行文件旁找不到游戏版本文件时会推断 v999.999.999。因此兼容性还以本轮真正导出游戏的模组加载验证为依据，不能只凭独立测试的版本推断。测试日志为 `work/headless-tests/full-run.log`、`run.log`，保存样例为 `roundtrip.save`，全部忽略；测试源码保存在 `tools/tests/`。

专用测试启动使用 `tools/play-test.ps1 start`。日志已证实进程 `user://` 落在仓库 `local/play-test/appdata/SlayTheSpire2`，并跳过 Steam 初始化。用户解锁后，已在专用测试档的图形界面启用模组并重启，主菜单明确显示加载了 2 个模组。用户继续操作其他窗口时，自动化检测到并发鼠标/键盘输入而停止，等待可独占前台的时间；角色选择、战斗界面和双端联机尚未实测。

另在全新的 `local/startup-test/appdata` 预置专用测试配置，运行真正安装的游戏 exe 的 headless 模式：BaseLib 282 个补丁成功、0 失败，Shenshen DLL/PCK 和 initializer 均实际加载，日志确认 Loaded 2 mods，13.051 秒到主菜单，退出码 0。这比程序集测试多验证了导出游戏的模组加载链，但仍不是角色选择和战斗画面实测。

该强制 headless 退出出现原生 `Invalid Task ID` 和 RID/资源未释放提示；在独立禁用全部模组的原版基线也复现同类提示（1 与 2 次 Invalid Task ID，其他 8 类 RID 数量相同），两者均无托管异常。不能把退出描述为完全无告警，也没有据此修改原版引擎。证据留在 `local/startup-test/` 与 `local/startup-vanilla/`。

日常档在启动前记录哈希；测试退出后用 `./tools/play-test.ps1 verify` 比较。游戏日志、专用存档、程序集、反编译资料和测试生成工程全部留在忽略目录，不能提交。

已对三个启动阶段后的日常存档做比较：1025 个文件的路径、长度和 SHA256 均未变化。

当前图形测试仍使用 `local/play-test/appdata` 的专用档，游戏 mods 中保留本轮 BaseLib/Shenshen 测试部署，成品另存 `dist/`。自动测试结束时保存过一份部署备份在忽略的 `local/retired-test-deployment/`。后续界面测试完成应退出该测试游戏，再运行 `tools/play-test.ps1 verify` 比对日常档；不要改用普通 Steam 启动进行开发实验。
